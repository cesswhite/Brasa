Expand the current character animation system substantially.

The existing sprite sheets should be treated as the canonical visual authority for each character.

Do not redesign the character when creating new animation frames.

Preserve exactly:

body proportions

head shape

horns

tail

clothing

armor

accessories

materials

color palette

lighting direction

outline treatment

rendering style

silhouette

character scale

The current sprite sheet contains useful major poses, but the game should not rely only on isolated static poses.

The objective is to create complete animation sequences that make combat feel responsive, fluid, physical, and visually satisfying.

========================================
CORE ANIMATION PRINCIPLE
========================================

Don't think:

"one sprite = one attack"

Think:

ANTICIPATION

→

MOVEMENT

→

IMPACT

→

REACTION

→

RECOVERY

Every important combat action should have enough frames to communicate these stages.

Do not create unnecessary frames purely to increase frame count.

Each frame should contribute to movement readability.

========================================
SPRITE GENERATION SYSTEM
========================================

For every existing character, create additional sprite sequences while preserving exact visual identity.

Whenever generating new sprites, use the existing approved sprite sheet as the strongest visual reference.

Never regenerate the character from a text description alone if a canonical sprite reference exists.

The new frames must look like they belong to the same original sprite sheet.

Maintain identical:

character dimensions

camera angle

perspective

rendering quality

scale

lighting

armor placement

costume details

body proportions

tail proportions

horn geometry

color relationships

The character must not slowly mutate between frames.

========================================
HIT REACTIONS
========================================

Create multiple hit reactions.

Do not reuse one generic damaged pose for every attack.

Possible reactions:

light hit

medium hit

heavy hit

head impact

body impact

low hit

critical hit

knockback

airborne hit

stagger

guard hit

status-effect reaction

low-health reaction

This creates significantly more combat variety.

The reaction selected should depend on the current combat event.

Example:

Quick Attack

→

small recoil

Heavy Attack

→

large torso recoil

Critical Hit

→

strong impact reaction

Charge Attack

→

knockback reaction

Signature Strike

→

special reaction

========================================
KNOCKBACK
========================================

Support knockback animations.

A powerful attack should be able to visually move the opponent backward.

Use:

impact frame

backward movement

balance-loss frame

recovery

Do not teleport characters between positions.

Godot may interpolate the current position while the sprite animation communicates physical reaction.

========================================
KNOCKDOWN
========================================

Create knockdown sequences.

Example:

heavy impact

→

loss of balance

→

fail

→

ground impact

→

lying state

→

stand-up animation

Not every attack should cause knockdown.

Reserve it for appropriate moves, critical events, special abilities, or specific combat mechanics.

========================================
KO
========================================

Do not transition instantly from standing to the existing defeated sprite.

Create a proper KO sequence.

Example:

final hit reaction

→

stagger

→

fail

→

ground impact

→

final KO pose

The final resting pose can reuse the existing defeated sprite where appropriate.

========================================
VICTORY
========================================

Create more than one victory animation where practical.

Possible examples:

raise fist

roar

relaxed pose

character-specific gesture

signature victory pose

Boss victory animation

These can later become unlockable cosmetic victory poses.

========================================
SPRITE EFFECTS

========================================
TRANSFORMATIONS
========================================

Support character transformations as a future-capable system.

A transformation is a temporary or persistent alternate visual/combat state.

Do not implement transformations as random sprite replacements.

A transformation should have:

transformation start animation

transition frames

transformed idle

transformed movement

transformed attacks

transformed hit reactions

transformed KO state where required

transformation end animation if reversible

Transformation data should be explicit.

Conceptually:

TransformationDefinition

id

character_id

trigger

duration

visual_form

stat_modifiers

move_changes

passive_changes

fx_theme

animation_set

Do not make transformation logic part of individual UI scenes.

========================================
TRANSFORMATION EXAMPLE
========================================

For a character similar to the current horned fighter, a transformation could visually evolve:

normal glowing chest core

→

core becomes brighter

→

energy travels through body cracks

→

eyes intensify

→

armor or skin gains controlled glowing details

→

transformed combat stance

Avoid completely redesigning the character.

The transformed version should remain immediately recognizable as the same fighter.

Transformation visual language should evolve existing character motifs.

========================================
TRANSFORMATION ANIMATION
========================================

A transformation could contain approximately:

preparation

energy buildup

body reaction

peak transformation frame

settling pose

transformed idle

Use particles and shaders for energy effects where possible rather than generating dozens of nearly identical character sprites.

========================================
SPRITE + GODOT HYBRID ANIMATION
========================================

Do not attempt to represent every movement exclusively through sprite frames.

Use a hybrid system.

SPRITES:

body pose

GODOT:

This gives significantly more fluidity without requiring hundreds of images per fighter.

========================================
HIT STOP
========================================

Add subtle hit-stop for powerful attacks.

When a strong attack lands:

briefly freeze or dramatically slow the visual action for a very small amount of time

then continue.

Keep it subtle.

Examples:

normal hit:
very small or no hit-stop

heavy hit:
small hit stop

critical:
stronger hit-stop

Signature Strike:
most noticeable hit-stop

The exact duration should be tuned during gameplay testing.

========================================
CAMERA RESPONSE
========================================

Allow attacks to request camera feedback.

Examples:

small hit:
no shake or extremely subtle shake

heavy hit:
small shake

critical:
medium shake

Signature Strike:
strong but controlled shake

Boss attacks:
context-dependent shake

Avoid constant camera shaking.

Impact loses meaning if every attack shakes the screen heavily.

========================================
ATTACK ANTICIPATION
========================================

Powerful attacks require readable anticipation.

Heavy attacks should visually communicate danger before they land.

Examples:

body leans backward

arm pulls back

stance lowers

energy gathers

feet reposition

Do not make all attacks start instantly.

Quick attacks can have little anticipation.

Heavy and Charge attacks should have more.

========================================
FOLLOW-THROUGH
========================================

Do not stop animations exactly at the impact pose.

Attacks need follow-through.

Example:

punch

→

extension

→

body continues slightly forward

→

arm returns

→

combat stance

This small detail dramatically improves perceived animation quality.

========================================
IN-BETWEEN FRAMES
========================================

Add transitional frames between important poses.

The current sprite sheet should be considered a collection of key poses.

Generate in-between frames when the transition between two existing poses feels abrupt.

Prioritize transitions with large silhouette changes.

Examples:

idle → punch

idle → crouch

idle → jump

attack → idle

hit → idle

standing → KO

Do not blindly interpolate every pose.

Create meaningful hand-authored or generated intermediate poses.

========================================
FRAME COUNT GUIDELINES
========================================

Do not enforce identical frame counts on every move.

As a starting point:

idle:
4–8 meaningful frames

quick attack:
4–6 frames

normal attack:
5–8 frames

heavy attack:
7–12 frames

charge attack:
8–14 frames

dash:
5–8 frames

jump attack:
7–12 frames

hit reaction:
3–6 frames

heavy hit:
4–8 frames

knockdown:
6–10 frames

stand-up:
5–8 frames

transformation:
8–16+ frames

Signature Strike:
10–20+ frames if justified

These are guidelines.

Animation quality is more important than arbitrary frame count.

========================================
ANIMATION SPEED
========================================

Separate animation frame count from animation playback speed.

Quick moves should play faster.

Heavy moves can contain more anticipation.

Transformations may be slower and more dramatic.

Do not assume all sprite animations use the same FPS.

Tune per animation.

========================================
SPRITE SHEET CONSISTENCY
========================================

All frames in one animation must share:

canvas size

character scale

ground baseline

pivot conventions

lighting

perspective

art style

transparent background

Do not allow the character to visually grow or shrink between frames unless the animation intentionally changes scale.

Keep the feet aligned consistently relative to the defined origin.

========================================
SPRITE ORIGIN
========================================

Defines a standard origin/pivot convention.

Prefer a ground-based pivot near the character's feet.

Every generated animation frame must respect it.

This prevents visual jitter when switching sprites.

========================================
SPRITE JITTER
========================================

When importing generated sprites, detect and correct frame-to-frame jitter.

The character should not shift horizontally or vertically because generated images were cropped differently.

Normalize:

canvas size

pivot

baseline

frame bounds

Do this during asset preparation.

========================================
ANIMATION STATE MACHINE
========================================

Create a proper fighter animation state system.

Possible states:

idle

moving

attacking

charging

airborne

hit

stagger

knockdown

recovery

transformation

special

victory

ko

Prevent impossible visual states.

For example:

do not start idle while the fighter is falling

do not play victory before KO resolution

do not play a second attack halfway through an uninterruptible heavy attack

========================================
INTERRUPTION RULES
========================================

Animations should define whether they can be interrupted.

Quick recovery may be interruptible.

Heavy attack wind-up may or may not be interruptible depending on gameplay.

Hit reactions normally interrupt appropriate offensive states.

KO interrupts everything.

Keep gameplay rules separate from purely visual transitions.

========================================
SPRITE ASSET GENERATION WORKFLOW
========================================

Before generating sprites for a move:

1. Inspect the canonical character sheet.

2. Defines the complete animation sequence.

3. Identify key poses.

4. Identify necessary transition frames.

5. Defines the character's body movement.

6. Defines which effects should be separate FX.

7. Generate the character frames.

8. Normalize frame dimensions and pivot.

9. Generate the FX sprites separately.

10. Import into Godot.

11. Set animation timing.

12. Add movement and effects.

13. Test at current gameplay speed.

14. Remove redundant frames.

15. Verify the character remains visually consistent.

========================================
GENERATIVE IMAGE RULE
========================================

Never generate an entire new animation without repeatedly comparing against the canonical character reference.

For every sprite-generation prompt, explicitly state that the character identity must remain identical.

Do not allow:

different horn sizes

different armor

missing accessories

different number of fingers

different tail

different chest symbol

different clothes

different proportions

different rendering style

different camera angle

different light sources

========================================

More frames are not automatically better.

Prioritize:

A carefully designed 6-frame attack can look better than a poorly generated 20-frame sequence.

Use Godot motion, particles, shaders, hit-stop, camera feedback, and FX to fill the gap between key sprites.
